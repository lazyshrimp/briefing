# 收盘简报 Software Development Workflow 设计

日期：2026-09-22  
输入规格：`requirement-analysis.md`（只读，本设计不改它）  
终点：一个交易日对应一份 A 股收盘简报，且通过该文件第 4 节的验收。  
不做：自动下单、个股榜、风格榜、改需求口径。

## 角色

| 角色 | 在本流程里做什么 | 不做什么 |
| --- | --- | --- |
| Workflow | 固定顺序。上一步的输出是下一步的输入 | 不根据心情改顺序，不跳过 Evaluator |
| Tool | 一次动作：读文件、算一个公式、写文件、跑测试 | 不解释市场，不改公式 |
| Skill | 一套方法：按规格调用多个 Tool，交出固定结构 | 不决定整个流程的下一步 |
| LLM | 只写市场评论；评论被拒时按失败原因重写一次 | 不改数字，不发明数据源 |
| Agent | 只在评估失败之后决定先查哪一类错误 | 不负责日常生成路径 |
| Evaluator | 对照需求第 4 节判定过或不过 | 不修改简报来让自己通过 |
| 人 | 批准实现计划、提供每周情绪数字、验收失败超过次数时拍板、收下交付 | 不每天确认均线和排名 |

日常生成是 Workflow。Agent 不出现在这条路上。Agent 只出现在「测试没过，下一步取决于失败内容」的时候。

## 总流程

```text
读取 requirement-analysis.md
    ↓
代码库理解 Skill
    ↓
影响分析
    ↓
实现计划 Skill → 人批准
    ↓
实现
    ↓
Build / Test Tool
    ↓
Evaluator
    ├─ 不过 → Agent 诊断 → 修改 → 再测（有次数上限）
    └─ 通过 → 人做代码评审
                ↓
        每日生成 Workflow
                ↓
        带日期的简报 + Evaluator 再跑一遍
```

## 开发阶段

### 1. 读取需求

- 角色：Tool `read_file`
- 输入：`notes/skills/requirement-analysis.md`
- 输出：规格文本。状态记为只读
- 失败：文件不存在或读失败 → 停止。不根据记忆继续
- 人：无

### 2. 代码库理解

- 角色：Skill。内部用 Tool `search_code`、`read_file`、`list_files`
- 输入：规格；`D:\canslim_standalone`；`C:\zd_pazq_hy`
- 输出：一张对照表。每个验收项对应「可抽用的现有函数」或「没有，需要新写」
- 失败：通达信目录不存在 → 停止，不换数据源。函数和选股逻辑缠在一起 → 记为「新写」，不在这一步改代码
- 人：无。这一步不改需求

这里没有 Agent。要读哪些路径，规格第 3.5 节已经写明。

### 3. 影响分析

- 角色：LLM 起草说明，Workflow 只要求它覆盖下面三行
- 输入：对照表
- 输出：会新增的程序、会读取的目录、明确不改的 canslim 选股与仓位逻辑
- 失败：输出里出现「顺手改需求」或「改用别的行情源」→ Evaluator 直接判失败，退回重写
- 人：确认「简报单独成程序，只读通达信和手工情绪表」

### 4. 实现计划

- 角色：Skill。LLM 起草，结构固定
- 输入：规格、对照表、已确认的影响分析
- 输出：步骤列表。每步有输入、输出、验证命令。覆盖信号、广度、两类前 10、情绪图、评论、一个已知交易日的对照数字
- 失败：某步没有验证命令 → 计划不合格，不进入实现
- 人：批准或退回。未批准不写实现代码

### 5. 实现

- 角色：按计划写代码。公式实现是 Tool 级行为，不在写代码时重新解释公式
- 输入：已批准的计划、规格
- 输出：可运行程序
- 失败：计划外想改口径 → 停止并问人。人不改 `requirement-analysis.md` 就不改程序行为
- 人：无，除非实现发现规格自相矛盾

### 6. 构建与测试

- 角色：Tool `run_test`
- 输入：程序、已知交易日的对照数据
- 输出：退出码、失败用例名
- 失败：构建失败或用例失败 → 进入诊断，不生成「正式简报」
- 人：无

### 7. Evaluator（开发结束时）

- 角色：Evaluator。逐条执行需求第 4 节
- 输入：测试结果、若已生成则加上样例简报
- 输出：`pass` 或失败项编号列表
- 失败：见下一节
- 人：无。判定规则是规格，不是感觉

### 8. 诊断与再测

- 角色：Agent。只在 Evaluator 不过时进入
- 输入：失败项编号、相关日志和文件路径
- 输出：一类原因：读错文件、公式与规格不一致、评论越界。然后修改对应处
- 失败：同一失败项超过约定次数仍不过 → 停止，把证据交给人。不改需求来迎合程序
- 人：超过次数后决定修程序、补数据，或停止
- 再测：Tool。跑同一组用例

通过之后：

### 9. 代码评审

- 角色：Skill。LLM 读 `git_diff`，对照规格和计划
- 输入：diff、规格、计划
- 输出：与规格不一致的列表。空列表表示未发现不一致
- 失败：发现不一致 → 回到实现，不交付
- 人：决定是否收下。不自动合并

## 每日生成 Workflow

开发阶段通过、人收下之后，每个交易日走下面这条。顺序固定。

### D1. 是否交易日

- 角色：Tool
- 输入：日期、交易日历
- 输出：`trading_day` 或 `skip`
- 失败：日历缺失 → 停止并写明缺失。不猜测「今天大概开市」
- 人：无
- `skip`：不生成简报，Workflow 结束

### D2. 读取通达信

- 角色：Tool
- 输入：`C:\zd_pazq_hy` 下规格点名的日线、`T0002/extdata`、板块与概念代码表
- 输出：原始记录，或某一项的 `missing`
- 失败：目录不是盘后已更新的数据 → 停止，不改用别的数据源。单条记录读不到 → 该项记 `missing`，其余继续
- 人：无

### D3. 计算信号、广度、榜单

- 角色：Skill。内部全是 Tool，公式来自规格第 3.1、3.2、3.5 节
- 输入：D2 的原始记录
- 输出：
  - 沪深300、创业板指各三个 YES/NO
  - 52 周新高减新低的净值（读 `extdata_13`）
  - 三个 50 日线以上比例
  - 当日 4%+ 涨/跌家数
  - 5 日、10 日突破比率；大于 1 标买盘占优；跌家数之和为 0 时写「无跌幅≥4%」
  - 滚动 60 日 25% 涨/跌家数与多空差
  - 板块、概念的当日前 10（按指数当日涨跌幅）
  - 板块、概念的 5/10/15/20 日前 10（按对应 extdata 的 RPS，旁边写指数区间涨跌幅）
- 失败：缺输入的格子写「缺失」。不补造，不用个股 RPS 填板块榜
- 人：无

### D4. 情绪

- 角色：Tool 写表和画图。数字来自人，不来自行情
- 输入：本周是否有新的看涨、看跌、横盘，以及历史序列
- 输出：数据日期、三个百分比、多空差、从第一条记录画到最新一周的图
- 失败：本周没有新数据 → 沿用上一周，不新作图。历史序列为空且本周也没填 → 情绪块写「缺失」
- 人：每周手工填一次三个百分比。不填则按失败处理，不让 LLM 猜测情绪

### D5. 市场评论

- 角色：LLM
- 输入：D3 和 D4 已经出现的数字。缺失项单独列出
- 输出：一段综合判断
- 失败：出现规格里没有的数字、买卖价或仓位 → Evaluator 拒绝。LLM 按拒绝原因重写一次。仍失败 → 评论写「缺失」，数字部分仍交付
- 人：无。不每天审评论，除非 D5 连续失败

### D6. 写出简报

- 角色：Tool
- 输入：D3、D4、D5
- 输出：带日期的简报文件
- 失败：写文件失败 → 停止，不声称已生成
- 人：无

### D7. 交付前 Evaluator

- 角色：Evaluator
- 输入：简报文件、需求第 4 节 11 条
- 输出：`pass` 或失败项列表
- 失败：数字类失败 → 回到开发阶段的诊断（Agent），不直接改简报文本凑数。只有评论失败 → 回 D5
- 人：`pass` 后自己使用这份简报。Workflow 不推送、不下单

## 谁不能越过谁

评论不能在 D3 完成之前写。Evaluator 不能通过改数来通过。Agent 不能在 D1–D7 这条日常路径上选择跳步。任何与 `requirement-analysis.md` 不一致的行为都是失败，不是新需求。
